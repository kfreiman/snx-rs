# Инфраструктура `tunnel1` и подключение к Xray

Это оперативная памятка о сервере и сервисах, проверенных **24 ноября 2026 года**. Состояние DNS, адресов, портов и программ может измениться; после изменений обновите эту страницу. Здесь намеренно нет паролей, UUID, REALITY-ключей, клиентской ссылки и секретного пути входа в панель. Не добавляйте эти данные в Git.

## Сервер и домен

- SSH alias: `tunnel1`; подключение: `ssh tunnel1`. Имя пользователя и адрес заданы в локальном SSH config.
- Домен: `t1.unitflow.dev`; на момент проверки DNS A указывал на `92.113.147.34`, публичной AAAA-записи не было.
- Система: Ubuntu 26.04.1 LTS.
- Для администрирования используйте `sudo` на сервере; клиентские VPN-команды запускайте от обычного пользователя.

## Сайт, nginx и TLS

На `http://t1.unitflow.dev` nginx перенаправляет HTTP на HTTPS. Сайт доступен по адресу [https://t1.unitflow.dev](https://t1.unitflow.dev); это самостоятельный статический макет, вдохновлённый RouterAI, **не официальный сайт RouterAI**. На странице нет форм входа и оплаты.

- Файлы сайта: `/var/www/t1.unitflow.dev/`.
- Конфигурация nginx: `/etc/nginx/sites-available/t1.unitflow.dev`, симлинк в `sites-enabled`.
- Nginx принимает TCP-подключения на 80 и 443. HTTP-01 challenge Certbot обслуживается через webroot `/var/www/t1.unitflow.dev`.
- Сертификат для `t1.unitflow.dev` выпущен Let’s Encrypt через Certbot. Включены HTTPS и HTTP/2. Автоматическое обновление обеспечивается `certbot.timer`; deploy hook проверяет конфигурацию и перезагружает nginx после обновления сертификата.
- Посмотреть актуальный сертификат: `ssh tunnel1 'sudo certbot certificates'`.
- Проверить тестовое обновление и deploy hook:

  ```bash
  ssh tunnel1 'sudo certbot renew --dry-run --run-deploy-hooks --cert-name t1.unitflow.dev --non-interactive --no-random-sleep-on-renew'
  ```

### Amnezia и порт 443

До настройки сайта TCP/UDP 443 занимал Docker-контейнер `amnezia-xray`; его сертификат был для `unitflow-tunnel1.duckdns.org`, а не для `t1.unitflow.dev`. По согласованию контейнер остановлен, сохранён, его restart policy установлена в `no`. Теперь TCP 443 занят nginx. `amnezia-telemt` и `amnezia-dns` этим переключением не останавливались.

**Не запускайте `amnezia-xray` поверх nginx:** сервисы претендуют на 443. Чтобы снова использовать Amnezia Xray на этом порту, сначала спланируйте перенос nginx HTTPS и изменение REALITY target/SNI; не меняйте Docker restart policy на `always`, пока конфликт не устранён.

## 3x-ui и клиентский VLESS + REALITY

На сервере работает официальный 3x-ui **v3.11.0** (`systemd` unit `x-ui`, автозапуск включён). Веб-панель слушает только `127.0.0.1:34913` и защищена случайным base path и логином/паролем. Не открывайте этот порт наружу.

Для входа:

1. Создайте SSH-туннель и оставьте его запущенным:

   ```bash
   ssh -N -L 127.0.0.1:18763:127.0.0.1:34913 tunnel1
   ```

2. В другом локальном терминале получите **только** реквизиты панели из root-only файла (там же есть API token, поэтому не используйте `cat` для всего файла):

   ```bash
   ssh tunnel1 "sudo grep -E '^(XUI_USERNAME|XUI_PASSWORD|XUI_WEB_BASE_PATH)=' /etc/x-ui/install-result.env"
   ```

3. Откройте `http://127.0.0.1:18763/<XUI_WEB_BASE_PATH>/` и войдите указанными логином и паролем. Путь, логин и пароль не публикуйте.

Для подключения к Xray настроен отдельный VLESS TCP/RAW + REALITY inbound на TCP **2053**:

- адрес клиента: `t1.unitflow.dev:2053`;
- REALITY SNI и имя сайта: `t1.unitflow.dev`;
- target REALITY: локальный nginx `127.0.0.1:443`;
- fingerprint: `chrome`; flow: `xtls-rprx-vision`.

REALITY-ключи, UUID и short ID не записываются в документацию. Чтобы получить готовую ссылку для доверенного клиента, используйте личный терминал:

```bash
ssh tunnel1 'sudo cat /etc/x-ui/t1.unitflow.dev-vless.txt'
```

VLESS-ссылка **является секретом доступа**. Передавайте её только клиенту по защищённому каналу; не вставляйте в Git, тикеты, общие чаты, командную строку или общедоступный файл. В Xray также остался отдельный inbound на 38824; не считайте его новым REALITY-подключением и не удаляйте, не проверив его назначение в панели.

На TCP 2096 работает отдельный сервер подписок 3x-ui без настроенного HTTPS для подписок. Не используйте и не распространяйте ссылки подписок по незащищённым каналам; для HTTPS сначала отдельно настройте TLS для этого сервиса.

## Импорт сервера в `dual-vpn`

`dual-vpn` использует **OneXrayCore**, но не читает выбранный сервер из открытого OneXray GUI. Xray-провайдер `dual-vpn` читает отдельный приватный профиль. В проверенной локальной конфигурации это `~/.config/xray-vpn/profile.json` (путь провайдера настраивается в `~/.config/dual-vpn/providers/personal.yaml`). Профиль существует, но его содержимое и соответствие серверу `t1.unitflow.dev` не проверялись. Импорт ниже заменяет профиль, который использует и `./xray-vpn`, и настроенный на этот путь Xray-провайдер `dual-vpn`.

1. Если профиль другого сервера нужен для отката, сохраните его в безопасное место вне репозитория. Не копируйте его в проект: `profile.json` содержит данные доступа.
2. Получите актуальную VLESS-ссылку из 3x-ui или по команде выше. Из корня репозитория выполните:

   ```bash
   ./xray-vpn import
   ```

   Вставьте ссылку в запрос `Вставьте ссылку VLESS (ввод не отображается)`. Ввод скрыт; не передавайте ссылку как аргумент командной строки и не публикуйте её.
3. Отключите и **закройте OneXray GUI** до запуска `dual-vpn`: GUI и CLI используют один тип процесса Core и могут остановить подключение друг друга.
4. Проверьте состояние:

   ```bash
   ./dual-vpn/dual-vpn status
   ```

   Если Xray уже работает под управлением `dual-vpn`, выполните **`restart`**, а не `start`: уже запущенный Core не переключится на импортированный профиль сам. Если `dual-vpn` не запущен, используйте `start`:

   ```bash
   ./dual-vpn/dual-vpn restart  # когда уже работает
   ./dual-vpn/dual-vpn start    # когда остановлен
   ./dual-vpn/dual-vpn status
   ```

   `restart` перезапускает все настроенные провайдеры `dual-vpn`, включая корпоративный Check Point; выполняйте его, когда допустимо переподключение обоих туннелей. Запускайте команды от обычного пользователя, **не через `sudo`**; CLI сам запросит системные привилегии.

`./xray-vpn import` принимает только VLESS с TCP/RAW + REALITY; неподдерживаемые транспорты отклоняются. Подробности о TUN, маршрутах, DNS и проверке — в [инструкции Xray CLI](xray-vpn.md) и [документации `dual-vpn`](../dual-vpn/docs/README.md).

## Основные проверки и резервная копия

```bash
ssh tunnel1 'sudo systemctl is-active nginx x-ui docker certbot.timer'
ssh tunnel1 'sudo nginx -t'
curl -I https://t1.unitflow.dev/
curl -I https://t1.unitflow.dev:2053/
```

Ответ `200` от HTTPS на 2053 проверяет REALITY fallback сайта, но **не** проверяет аутентификацию VLESS-клиента. Проверяйте подключение самим VPN-клиентом.

При переключении создана защищённая root-only резервная копия `/root/t1-site-rollback.ig14h0ij` (база 3x-ui, старые настройки inbound, ссылка клиента, прежний HTTP-конфиг nginx и restart policy Amnezia). В резервной копии лежат секреты; не скачивайте её в репозиторий, не публикуйте и не восстанавливайте вслепую. Перед откатом остановите/перенастройте конфликтующие сервисы на портах 80/443.
