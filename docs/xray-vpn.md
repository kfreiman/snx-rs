# Xray из терминала вместе с Check Point

`./xray-vpn` запускает установленный **OneXrayCore** без GUI и создаёт Linux
TUN-интерфейс. Это отдельный инструмент: `run_combined_vpn.sh` он не изменяет и
пока не запускает. Поддерживается экспорт **VLESS + TCP/RAW + REALITY**;
другие транспорты и параметры не игнорируются, а отклоняются при импорте.

## Требования

- Linux, Python 3 с `python3-dbus`, `sudo` и работающий `systemd-resolved` с
  системным DNS-stub `127.0.0.53`.
- Установленный OneXray с `/opt/OneXray/OneXrayCore`, поддерживающим TUN,
  автоматические маршруты и DNS outbound. Проверено с OneXrayCore Xray 26.10.31. Другой путь
  можно передать через `--core PATH` или `XRAY_CORE`.
- Доступ к `/dev/net/tun` и IPv4-адрес сервера Xray. Для запуска и остановки CLI
  запросит `sudo`.

Отключите и **закройте OneXray GUI до запуска CLI**: GUI и CLI используют один
тип процесса Core и могут остановить подключение друг друга. Сам Check Point в
`snx-rs-gui` отключать не нужно.

## Подключение

Импортируйте экспорт OneXray один раз:

```bash
./xray-vpn import
```

Вставьте ссылку `vless://...` и нажмите Enter. Ввод не отображается и не
попадает в историю оболочки. Если ссылка уже сохранена в приватном файле,
используйте `./xray-vpn import --file /путь/к/ссылке` или передайте её через
stdin с `./xray-vpn import --stdin`. Не записывайте ссылку в командную строку,
репозиторий или общедоступный файл.

```bash
./xray-vpn start
./xray-vpn status
./xray-vpn logs
./xray-vpn stop
# либо ./xray-vpn restart
```

Запускайте команды от обычного пользователя, не через `sudo`: CLI сам запросит
права для своего процесса. При `start` проверяется HTTPS-запрос к
`api.ipify.org` **через созданный интерфейс**, и выводится внешний IPv4. Если
проверка не прошла, запуск отменяется и Xray останавливается. В закрытой сети
доступен `start --skip-probe`, но в этом режиме запуск процесса не подтверждает
доступность сервера. `status` возвращает код 0 для работающего процесса и 1 для
остановленного или некорректного состояния; состояние не является постоянной
проверкой доступа к серверу.

Профиль хранится в `~/.config/xray-vpn/profile.json`, а временный конфиг,
состояние процесса и журнал — в `~/.local/state/xray-vpn/` (учитываются
`XDG_CONFIG_HOME` и `XDG_STATE_HOME`). Каталоги имеют права `700`, файлы —
`600`. Профиль содержит UUID и другие данные доступа; не публикуйте его.
Запросы пользователей Xray в журнал не записываются. После остановки временный
конфиг удаляется.

## Маршруты и DNS

CLI рассчитан на **split-tunnel Check Point**, уже подключённый через `snx-rs`:

- Он обнаруживает правило `snx-rs` в таблице `18000`, оставляет адрес шлюза
  Check Point и адрес сервера Xray на прежнем маршруте и не меняет
  корпоративные policy rules. Подсети Check Point продолжают использовать его
  интерфейс. Если другой full-tunnel с более приоритетным правилом перехватывает
  интернет, запуск завершается ошибкой.
- Существующие более конкретные IPv4-маршруты основной таблицы, в том числе
  локальные сети, остаются вне Xray; остальной IPv4-трафик идёт в TUN. IPv6
  тоже направляется в TUN, кроме более конкретных существующих маршрутов, если
  IPv6 включён. Явные IPv4-исключения можно
  повторять: `./xray-vpn start --bypass 203.0.113.10/32 --bypass 192.0.2.0/24`.
- `systemd-resolved` получает на TUN маршрутизируемый домен `~.` через D-Bus.
  Публичный DNS идёт через Xray к `1.1.1.1`, а более специфичные корпоративные домены
  продолжают использовать DNS Check Point. Приложения с собственным DNS или
  привязкой к физическому интерфейсу могут вести себя иначе.

Адреса исключений определяются **при запуске**. После переподключения Check
Point, смены его шлюза или смены локальной сети перезапустите Xray. Если Xray
нужно запустить *до* Check Point, заранее передайте IPv4 шлюза Check Point в
`--bypass`; иначе его транспорт может попасть в Xray. Для использования из
`run_combined_vpn.sh` этот адрес и порядок запуска нужно настроить отдельно.
DNS-имя сервера Xray разрешается при каждом запуске; после смены его IP также
нужен перезапуск.

**Это не kill switch.** Если Core аварийно завершится, TUN исчезнет, и система
снова может направлять трафик через обычный uplink. Уже существующие конкретные
маршруты и заданные исключения тоже обходят Xray. Если управляющий процесс
завершился, а Core остался работать, `status` попросит выполнить `stop`.

## Проверка

Модульные тесты без прав администратора:

```bash
python3 -m unittest discover -s tests -p 'test_xray_vpn.py' -v
```

Подключение, IPv4/IPv6, UDP, публичный и корпоративный split DNS, приоритет
корпоративного маршрута, восстановление маршрутов и аварийное завершение Core
проверялись в отдельной Ubuntu 24.04 VM. Существующее подключение Check Point на
хосте при тестировании не отключалось и не перенастраивалось.
